> **项目定位**：小组内网协作的脚本共享系统，支持版本管理、权限控制、小组共享。
> **技术栈**：纯 Node.js 零依赖（无任何 npm 包），SQLite 存储（node:sqlite），原生 HTML/CSS/JS 前端。
> **架构**：分层架构 Router → Controller → Service → Repo，职责清晰，便于扩展。
> **本文定位**：上一篇《「脚本仙人」系统开发总结》的完善优化篇，重点补充部署实战经验。

## 一、为什么做这个项目

在小组日常开发中，经常需要共享部署脚本、工具脚本、配置文件。传统的做法是：

- 发到群里 / 网盘 —— 版本混乱，谁改了什么说不清
- 用 Git 仓库 —— 对非开发同学不友好，且脚本经常要"临时改一版"
- 用现成的文件共享工具 —— 没有版本管理，没有权限控制

于是我们决定自己写一个**面向小组内网协作的脚本共享系统**，核心诉求：

1. **共享脚本**：小组内网成员都能上传、下载、预览脚本
2. **版本管理**：脚本可以多版本迭代，支持历史查看、回滚、更新说明
3. **权限控制**：只有 owner 能改/删/共享，可读用户只能看
4. **零依赖**：纯 Node.js 原生实现，`node server.js` 就能跑，不依赖任何构建工具

> 为什么零依赖？因为公司安全软件会拦截 esbuild / vite 等构建工具，纯原生实现可以完全避开这些麻烦。

## 二、技术选型

| 技术 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js 24+ | 原生支持 `node:sqlite`，无需额外安装数据库 |
| 数据库 | SQLite（node:sqlite） | 单文件、零配置、适合小组规模 |
| 密码哈希 | scrypt（node:crypto） | Node 内置，安全可靠 |
| HTTP 服务 | node:http | 原生，不依赖 express |
| 前端 | 原生 HTML/JS | 无构建，直接静态托管 |
| 部署 | start.bat / stop.bat | Windows 内网后台常驻 |

**核心决策：零 npm 依赖。** 整个项目只用 Node.js 内置模块（`node:http`、`node:crypto`、`node:sqlite`、`node:fs` 等），这是本项目最大的特色，也是工程化落地的重要考量。

## 三、架构设计

### 3.1 严格分层

项目采用经典的分层架构：**Router(路由) → Controller(控制器) → Service(业务) → Repo(数据)**

```
请求进入
   │
   ▼
server.js                 ★ 入口层：启动、装配、优雅退出、初始化、数据迁移
   │
   ▼
app.js                    ★ 装配层：注册路由表 + 中间件 + 全局错误边界
   │
  ├── middleware/auth.js   ★ 中间件：Bearer token 鉴权
   │
   ▼
modules/<name>/
   ├── *.routes.js        ★ 路由层：声明接口地图
   ├── *.controller.js    ★ 控制器层：解析 HTTP 请求/响应
   ├── *.service.js       ★ 服务层：业务规则校验，编排数据
   └── *.repo.js          ★ 数据层：封装存储（SQLite + 磁盘文件）
   │
   ▼
utils/                    ★ 工具层：http / logger / password / sqlite / audit
```

### 3.2 各层职责

| 层 | 文件 | 职责 | 类比 |
|---|---|---|---|
| 入口层 | `server.js` | 启动、监听、优雅退出、初始化、数据迁移 | 大门 |
| 装配层 | `app.js` | 组装所有模块、注册路由、全局错误边界 | 前台调度 |
| 中间件 | `middleware/auth.js` | 请求身份校验 | 门卫 |
| 路由层 | `*.routes.js` | 接口地图（who→what） | 菜单 |
| 控制器层 | `*.controller.js` | 解析 req/res，转 HTTP 语义 | 服务员 |
| 服务层 | `*.service.js` | 业务规则、编排 | 厨师 |
| 数据层 | `*.repo.js` | 读写存储 | 仓库 |
| 工具层 | `utils/*.js` | 公共设施 | 公共设施 |

### 3.3 依赖方向

```
Controller → Service → Repo（依赖向下）
上层只依赖下层的接口，下层不认识上层。
→ 换存储(Repo)或换框架(Controller)不影响其他层。
```

这种设计带来的好处：
- **单一职责**：每个文件只做一件事
- **开闭原则**：加新模块只需在 app.js 注册，不改核心
- **可测试性**：各层可以独立 mock 测试
- **可维护性**：业务逻辑集中在 Service，数据访问集中在 Repo

## 四、核心功能

### 4.1 认证与用户
- 登录签发带过期时间的 token，连续失败锁定账号
- 注册新用户，密码 scrypt 哈希存储
- 管理员可禁用/启用用户、改角色、重置密码

### 4.2 文件 / 脚本管理
- 上传：支持文本/脚本（JSON）和任意文件（multipart/form-data）
- 下载：流式下载，正确文件名和 MIME
- 在线预览：文本类文件直接预览
- 搜索：按文件名 / 简介 / 标签 模糊搜索
- 标签：上传/编辑时打标签，彩色标签云，点击一键筛选
- 筛选：按上传者 / 文件类型 / 标签 组合筛选，按名称/时间/大小排序

### 4.3 脚本版本管理（核心）
- 新增版本：为脚本添加新版本，可填更新说明
- 版本历史：查看所有版本（版本号/大小/更新人/时间/说明）
- 查看版本：查看任意历史版本内容
- 回滚：一键回滚到指定版本（切换当前版本指针，保留全部历史）

### 4.4 小组共享
- 共享给成员：指定用户名列表，共享给特定成员
- 小组公共：设为公共文件，所有人可见
- 权限控制：只有 owner 能改/删/共享；可读用户能下载/预览/看版本

### 4.5 运维
- 健康检查：`GET /api/health` 返回状态、磁盘、文件数、用户数
- 审计日志：上传/下载/删除/版本/共享等操作记录到 SQLite + audit.log
- 运行日志：按天滚动落盘到 data/logs/
- 备份：backup.bat 一键备份 data/ 目录

## 五、遇到的问题与解决方案

开发过程中踩了不少坑，这里重点记录两个**部署阶段**遇到的实际问题。

### 5.1 问题一：端口号被占用

**现象：**

在小组内网部署时，双击 `start.bat` 启动服务，但服务一直启动失败。查看日志发现：

```
Error: listen EADDRINUSE: address already in use :::3000
```

**原因分析：**

3000 端口已经被其他进程占用了。排查后发现，之前手动启动过服务（`node server.js`），进程没有正常退出，一直占着 3000 端口。再次启动时，新进程无法绑定端口，直接报 `EADDRINUSE` 错误。

更隐蔽的情况是：**某个 node 进程占用了 3000 端口，但没有 PID 文件记录**，导致 `stop.bat` 无法通过 PID 文件找到并停止它。

**解决方案：**

1. **用 PID 文件精确定位进程**：服务启动时把 `process.pid` 写入 `data/server.pid`，停止时读取 PID 文件精确结束对应进程，而不是粗暴地 `taskkill /F /IM node.exe`（那会误杀所有 node 进程）。

```js
// server.js 启动成功后写入 PID
server.listen(config.port, config.host, () => {
  writeFileSync(PID_FILE, String(process.pid), 'utf8')
})
```

2. **start.bat 启动前检查端口**：通过 `netstat -ano | findstr :3000` 检查端口是否被占用，若被占用则提示先停止旧进程。

3. **stop.bat 只杀 FileHub 进程**：读取 PID 文件，用 `taskkill /F /PID %PID%` 只结束 FileHub 进程，不影响其他 node 程序。

```bat
REM stop.bat 核心逻辑
set /p PID=<"%PID_FILE%"
taskkill /F /PID %PID%
```

> **经验总结**：后台服务一定要用 PID 文件管理进程生命周期，避免"僵尸进程"占用端口。同时，停止脚本要精确定位目标进程，不要用 `taskkill /IM` 误杀所有同名进程。

### 5.2 问题二：内网 IP 地址会变

**现象：**

服务启动后，`start.bat` 显示访问地址 `http://<本机内网IP>:3000/`，但同事反馈"昨天还能访问，今天打不开了"。

**原因分析：**

小组内网使用 **DHCP 动态分配 IP**，服务器的内网 IP 地址**每天可能变化**。昨天是 `10.26.55.129`，今天可能就变成 `10.26.55.130` 了。如果 `start.bat` 里硬编码了 IP，IP 一变就失效。

**解决方案：**

写一个 PowerShell 脚本 [`get-lan-ip.ps1`](get-lan-ip.ps1)，**每次启动时实时检测当前内网 IP**，而不是硬编码：

```powershell
# get-lan-ip.ps1 — 获取当前活动网卡的内网 IPv4 地址
$ip = (Get-NetIPConfiguration |
    Where-Object { $_.IPv4DefaultGateway -ne $null -and $_.NetAdapter.Status -eq 'Up' } |
    Select-Object -First 1).IPv4Address.IPAddress

# 若未找到，回退到任意非回环 IPv4 地址
if (-not $ip) {
    $ip = (Get-NetIPAddress -AddressFamily IPv4 |
        Where-Object { $_.IPAddress -notlike '127.*' -and $_.IPAddress -notlike '169.254.*' } |
        Select-Object -First 1).IPAddress
}

# 最终回退到本机回环
if (-not $ip) { $ip = '127.0.0.1' }

Write-Output $ip
```

然后在 `start.bat` 中调用它，把检测到的 IP 显示给用户：

```bat
REM start.bat 自动检测当前内网 IP
for /f "delims=" %%i in ('powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0get-lan-ip.ps1"') do set LAN_IP=%%i
if not defined LAN_IP set LAN_IP=127.0.0.1

echo   访问地址: http://%LAN_IP%:3000/
```

这样无论 IP 怎么变，`start.bat` 都会显示当前正确的内网访问地址。

> **经验总结**：内网部署时，IP 是动态的，不要硬编码。用脚本实时检测，或者用主机名（如 `http://server-name:3000/`）代替 IP。

### 5.3 问题三：批处理文件中文乱码

**现象：**

`start.bat` 和 `stop.bat` 里写了中文提示，但运行时中文变成乱码，甚至报"不是内部或外部命令"。

**原因分析：**

Windows cmd 默认使用 **GBK 代码页（936）**，而文件保存为 **UTF-8 编码**。UTF-8 的中文字节在 GBK 下被错误解码，导致中文被当作命令执行。

**解决方案：**

将 `.bat` 文件保存为 **GBK 编码**（Windows 中文系统标准），与 cmd 默认代码页匹配，中文正常显示。

> **经验总结**：Windows 批处理文件的中文编码要与 cmd 代码页一致。中文 Windows 系统用 GBK，否则中文会乱码。

## 七、用到的架构思想（面试/学习点）

| 思想 | 体现 |
|---|---|
| **分层架构** | Controller/Service/Repo 职责分离 |
| **控制反转(IoC)** | server 只调 app.handle，不碰业务 |
| **单一职责(SRP)** | 每个文件只做一件事 |
| **依赖倒置** | 上层依赖下层接口，不依赖实现 |
| **开闭原则** | 加新模块只需在 app.js 注册，不改核心 |
| **防御性编程** | 路径穿越校验、body 大小限制、token 防篡改 |
| **元数据与文件分离** | 元数据在 SQLite，本体在 uploads 目录 |
| **全局错误边界** | 所有异常统一转 500，不崩溃进程 |

## 八、总结

这个项目虽然规模不大，但完整地实践了：

1. **工程化落地**：从需求分析、分层架构、到部署运维，全流程覆盖
2. **零依赖哲学**：只用 Node 原生模块，避开构建工具和外部依赖的坑
3. **防御性编程**：路径穿越、body 限制、token 防篡改等安全措施
4. **部署实战**：解决了端口占用、动态 IP、中文编码等真实部署问题

最有价值的不是代码本身，而是**踩坑后沉淀的经验**：

- 后台服务要用 PID 文件管理进程，避免僵尸进程占端口
- 内网 IP 是动态的，不要硬编码，要实时检测
- Windows 批处理文件的中文编码要与 cmd 代码页一致
